Browser workbench

How local SceneDetect analysis works

The workbench is a static GitHub Pages application. It reads the video you choose in your browser, samples decoded frames, and passes RGB pixels to scenedetect-rs compiled to WebAssembly. The media file itself is not uploaded to a server.

Your video stays on this device

Selecting a file creates a browser-local object URL. The video element decodes that local file, and the workbench reads presented frames into a canvas. No upload endpoint is involved in the analysis path.

Sampling controls the browser workload

The analysis frame rate determines how often the browser samples the video timeline. A higher rate gives finer boundary timing but processes more frames. The maximum frame dimension limits the RGB image sent into Rust and can be lowered for faster analysis.

Rust owns detection semantics

Detector defaults, scoring, thresholds, minimum scene length behavior, scene construction, and supported boundary-review decisions come from scenedetect-core. The browser layer is responsible for local media decoding, presentation synchronization, controls, and rendering results.

Browser frames are synchronized before detection

When supported, the workbench waits for requestVideoFrameCallback before reading canvas pixels so analysis follows a frame actually presented by the browser. A conservative animation-frame fallback is used where that API is unavailable, and decreasing media times are rejected before pixels enter the Rust session.

What the browser version does not claim

Browser decoding is useful for a local, install-free workflow, but it does not claim native FFmpeg frame-exact or variable-frame-rate timestamp parity. The sampled browser timeline is explicit in the results so those limits remain visible.
